# گزارش تغییرات داشبورد — برای بررسی تحلیلگر نرم‌افزار

این سند مخصوص یک تغییر مشخص است (نه کل پروژه): بازطراحی صفحهٔ داشبورد پنل
مدیریت کلینیک. هدف این است که یک تحلیلگر نرم‌افزار بتواند بدون نیاز به دیدن
کل تاریخچهٔ پروژه، دقیقاً بفهمد چه چیزی و چرا تغییر کرده و نظر فنی بدهد.

## ۱. درخواست اولیه (خلاصه)

سه تغییر روی صفحهٔ `/dashboard` خواسته شد:

1. ظاهر کلی صفحه «زنده‌تر و مدرن‌تر» شود (بدون شلوغ‌کاری).
2. بخش «نوبت‌های پیش‌رو» به‌صورت لیست مرتب و گروه‌بندی‌شده بر اساس روز
   (امروز/فردا/تاریخ) نمایش داده شود.
3. کلیک روی «ثبت نوبت جدید» به‌جای رفتن به صفحهٔ جدید، یک **پاپ‌آپ (مودال)**
   همان‌جا باز کند؛ بعد از ثبت موفق، پاپ‌آپ بسته شود و لیست به‌روز شود.

## ۲. خلاصهٔ راه‌حل

### ۲.۱. ظاهر (item 1)

در `app/globals.css`، کلاس مشترک `.card` (که همهٔ کارت‌های پنل از آن استفاده
می‌کنند) سایه‌اش عمیق‌تر و نرم‌تر شد و یک کلاس اختیاری جدید `.card-hover`
اضافه شد (سایه/جابه‌جایی ملایم روی هاور). این کلاس فقط روی کارت‌های آماری
(«پزشکان»، «نوبت‌های امروز» و ...) در داشبورد اعمال شده، نه همهٔ کارت‌های
سایت — تغییر عمدی و محدود، نه یک ری‌دیزاین کامل.

### ۲.۲. لیست گروه‌بندی‌شده (item 2)

کامپوننت جدید `app/dashboard/UpcomingList.tsx` (Server Component) اضافه شد.
منطقش خیلی ساده است: چون کوئری نوبت‌ها از قبل بر اساس `startTime` مرتب
(`orderBy: { startTime: "asc" }`) برمی‌گردد، فقط کافی است در یک پاس روی آرایه
حرکت کنیم و هر جا کلید روز (`YYYY-MM-DD`) عوض شد، یک گروه جدید باز کنیم —
پیچیدگی زمانی خطی، بدون کوئری اضافه به دیتابیس. برچسب هر گروه «امروز»/«فردا»
یا تاریخ کامل فارسی است.

### ۲.۳. پاپ‌آپ ثبت نوبت (item 3، مهم‌ترین بخش)

اینجا مهم‌ترین تصمیم معماری گرفته شد: **به‌جای ساخت یک مسیر ثبت نوبت جداگانه
و موازی برای پاپ‌آپ، همان منطق و همان Server Action صفحهٔ کامل نوبت‌دهی
(`/book/[doctorId]`) دوباره استفاده شد.**

- منطق ساخت «شبکهٔ ماهانه» (کدام روزها کاری‌اند، چند ساعت خالی دارند) که قبلاً
  مستقیم داخل `app/book/[doctorId]/page.tsx` نوشته شده بود، به یک تابع مستقل
  و قابل‌استفادهٔ مجدد به اسم `buildMonthGrid` در `lib/booking.ts` منتقل شد.
  الان هم صفحهٔ کامل نوبت‌دهی و هم پاپ‌آپ داشبورد از **همان یک تابع** استفاده
  می‌کنند — یعنی هیچ‌وقت این‌دو نمی‌توانند در تشخیص «این ساعت خالی است یا نه»
  از هم عقب بیفتند یا نتیجهٔ متفاوت بدهند.
- دو Server Action سبک و فقط برای «خواندن» داده اضافه شد
  (`getQuickBookCalendarAction`, `getQuickBookSlotsAction` در
  `app/actions/booking.ts`) که همان `buildMonthGrid`/`getSlotsForDay` را صدا
  می‌زنند و نتیجه را به‌شکل داده‌ی قابل سریال‌سازی (نه شیء `Date` خام) برای
  کامپوننت کلاینت برمی‌گردانند.
- برای **ثبت واقعی نوبت**، پاپ‌آپ هیچ منطق جدیدی ندارد؛ دقیقاً همان
  `createManualAppointmentAction` را که فرم صفحهٔ اصلی هم استفاده می‌کند صدا
  می‌زند. یعنی قفل ضدتداخل نوبت (unique constraint دیتابیس + تراکنش اتمیک در
  `bookAppointment`) دقیقاً همان چیزی است که قبلاً بود و تغییری نکرده — فقط
  یک رابط کاربری جدید (پاپ‌آپ) روی همان هستهٔ قبلی سوار شده.
- کامپوننت کلاینت جدید `app/dashboard/QuickBookModal.tsx`: state محلی برای
  ماه/روز/ساعتِ انتخاب‌شده، `useActionState` برای فرم ثبت (همان الگویی که در
  `BookingForm.tsx` قبلی هست)، و بعد از ثبت موفق `router.refresh()` می‌زند تا
  داشبورد (آمار + لیست نوبت‌ها) بدون رفرش کامل صفحه به‌روز شود، سپس پاپ‌آپ را
  می‌بندد.
- کامپوننت `app/dashboard/NewAppointmentCard.tsx` بنر «ثبت نوبت جدید» را
  رندر می‌کند و فقط مسئول باز/بسته‌کردن پاپ‌آپ برای پزشک انتخاب‌شده است.

**صفحهٔ کامل `/book/[doctorId]` دست‌نخورده باقی ماند** (فقط منطق تکراری‌اش
استخراج شد، رفتارش عوض نشده) — چون هنوز از داشبورد پزشکان (`/dashboard/doctors`)
و از جاهای دیگر لینک می‌شود و ریسک شکستن آن مسیر را نمی‌خواستم بپذیرم.

## ۳. فایل‌های تغییریافته/اضافه‌شده

| فایل | نوع تغییر | توضیح |
|---|---|---|
| `lib/booking.ts` | تغییر | استخراج `buildMonthGrid` (منطق مشترک شبکهٔ ماهانه) |
| `app/book/[doctorId]/page.tsx` | تغییر | استفاده از `buildMonthGrid` به‌جای کد تکراری |
| `app/actions/booking.ts` | تغییر | دو Server Action جدید فقط-خواندنی برای پاپ‌آپ |
| `app/dashboard/QuickBookModal.tsx` | جدید | خود پاپ‌آپ (تقویم + ساعت‌ها + فرم) |
| `app/dashboard/NewAppointmentCard.tsx` | جدید | بنر CTA + مدیریت باز/بسته‌بودن پاپ‌آپ |
| `app/dashboard/UpcomingList.tsx` | جدید | لیست گروه‌بندی‌شدهٔ نوبت‌های پیش‌رو |
| `app/dashboard/page.tsx` | تغییر | استفاده از دو کامپوننت بالا، فاصله‌گذاری صفحه |
| `app/globals.css` | تغییر | سایهٔ عمیق‌تر `.card` + کلاس `.card-hover` |
| `tests/booking.test.ts` | تغییر | ۳ تست جدید برای `buildMonthGrid` |

## ۴. تست‌ها و تاییدها

- ۵۸ تست خودکار (`npm test`) سبز — شامل ۳ تست جدید مخصوص `buildMonthGrid`
  (شمارش صحیح ساعت خالی، روزهای غیرکاری، روزهای گذشته/امروز).
- `tsc --noEmit` و `eslint` بدون خطا.
- `next build` (production) بدون خطا.
- مسیر کامل با مرورگر خودکار (Playwright) به‌صورت زنده تست شد: باز کردن
  پاپ‌آپ، رفتن بین ماه‌ها، انتخاب روز/ساعت، ثبت نوبت واقعی، بسته‌شدن خودکار
  پاپ‌آپ، و به‌روزشدن آمار + لیست «نوبت‌های پیش رو» بدون رفرش دستی — بدون خطای
  کنسول.

## ۵. چیزهایی که نظر شما را می‌خواهم

1. **انتخاب معماری پاپ‌آپ**: به‌جای مسیر/صفحهٔ جدا، از همان Server Action و
   همان تابع منطق ماهانه استفاده شد تا هیچ منطق نوبت‌دهی دوباره نوشته نشود.
   آیا این رویکرد (duplicate presentation, single source of truth for logic)
   را درست می‌دانید یا ترجیح می‌دادید پاپ‌آپ کاملاً مستقل باشد؟
2. **مدیریت state پاپ‌آپ**: state تقویم/ساعت به‌صورت کاملاً محلی (client-side)
   نگه داشته می‌شود و با `Server Action` که مستقیم از کامپوننت کلاینت صدا زده
   می‌شود داده می‌گیرد (نه یک API route جدا). آیا این الگو (Server Action به
   جای Route Handler) برای این حجم کار مناسب است؟
3. **`router.refresh()` بعد از ثبت**: چون `createManualAppointmentAction` از
   قبل `revalidatePath("/dashboard")` را صدا می‌زند، تئوریاً کش صفحه به‌روز
   می‌شود؛ اما برای اطمینان `router.refresh()` هم در کلاینت صدا زده شده
   (بی‌ضرر ولی شاید تکراری). نظرتان دربارهٔ حذف یکی از این دو چیست؟
4. هر نکتهٔ دیگری که در کدهای بالا (به‌خصوص `QuickBookModal.tsx`) از نظر
   خوانایی، کارایی یا الگوهای React/Next.js به نظرتان قابل بهبود می‌آید.
